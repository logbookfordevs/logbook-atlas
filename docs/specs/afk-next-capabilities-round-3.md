# AFK Next: third proposal

Status: broad proposal for collaborative refinement; no catalog migration or skill implementation yet.
Date: 2026-09-17.
Inventory: the current default-catalog manifest contains 52 entries: 33 manual and 19 automatic. “Default catalog” includes optional entries; it does not mean all are installed by default.

## Direction

Build **substantive, manually invoked AFK workflows**, using source composition for current manual operations and behavioral composition with independently available automatic capabilities. Consider the whole catalog. Restore the breadth of the initial capability exploration without carrying forward round two's conservative exclusions.

The manual boundary determines what we incorporate, not how ambitious a workflow may be. Design can govern a complete design engagement while using full Impeccable. Plan can incorporate Wayfinder's decision-map method. Implement can own tracked delivery. These are workflows with outcomes, methods, artifacts, and editorial judgments, rather than new names for selecting old skills.

AFK owns reconciliation in both architectural alternatives. Independent source maintenance does not mean unresolved policy. AFK must decide where methods overlap, what takes priority, which evidence counts, and when one method gives way to another. Agents apply those rulings; they should not have to reinvent them on every run.

This proposal resets earlier tentative standalone preferences for non-tool manual skills. Automatic skills remain independently addressable under the selected strategy, including Truss and Writing for Agents. Library- and tool-specific packages remain independent catalog entries with no umbrella membership. All their operations are still accounted for below. Nothing is silently retired for failing to fit a category.

The [second proposal](afk-next-capabilities-round-2.md) is historical. Its five-workflow limit, exclusion of Design, and decision to leave Wayfinder and ADF outside source composition are superseded here.

## Comparison with the first capability map

The first map proposed eleven work capabilities and three supporting capabilities: fourteen total. Round three reuses twelve of those names and adds Describe as an explicit workflow. Two previous capabilities are incorporated into other workflows rather than removed as operations:

| First map | Third proposal |
|---|---|
| Specify | Spec synthesis is a method within Plan |
| Continue | Context transfer is in Communicate; recovery remains with Implement, Plan, and Coordinate as relevant |
| Existing-behavior documentation within broader communication scope | Describe is now an explicit workflow, drawing on PE Product Description |

Investigate, Diagnose, Decide, Design, Plan, Implement, Review, Verify, Communicate, Learn, Coordinate, and Configure retain their names, although their boundaries and composition are revised. The first map described capabilities without committing to one skill per row; round three positively proposes manual workflow entries. Thus the change is fourteen capability labels to thirteen proposed workflow entries, not a simple rename of an already approved catalog.

## Architecture: three different responsibilities

| Responsibility | What AFK owns | What it does not imply |
|---|---|---|
| Source composition | Selected manual source material, adaptations, methods, assets, scripts, and their provenance | Copying every upstream file or retaining every upstream root as a nested skill |
| Behavioral composition | Explicit use of independent capabilities, the task given to each, relevant conditions, and integration of results | Absorbing those capabilities or losing their direct invocation |
| Editorial policy | Conflict rulings, contextual priorities, output contracts, and compatibility decisions | A generic “use your judgment” instruction or a hierarchy overriding user/host instructions |

Compass may lose its separate job and be retired as the workflows become clearer. Its distilled routing knowledge should survive in the relevant methods and shared rulings; retaining its catalog entry is provisional, not an architectural requirement. If a distinct navigation need remains, Compass can serve it. Each workflow owns doing its job regardless of whether Compass remains. A short root can select a method while the package as a whole contains substantial functionality. Moving detail into references must not turn functionality into an unimplemented promise to call another skill.

Automatic/manual policy is a revisable default, not an intrinsic property of a method. Changing a user's local invocation setting must not silently change package ownership. Matt's Prototype is automatic in this inventory; Leonardo has explicitly reopened whether its default should become manual. This proposal integrates it behaviorally and records structural incorporation as an available follow-up, without assuming the policy change is decided.

## Proposed capability surface

All thirteen entries below are proposed manual workflows. Names are working labels. Some incorporate several manual sources; others add an AFK-owned method around existing independent capabilities. A workflow need not have several source ancestors to have useful functionality.

| Workflow | Description sketch | Functionality it owns |
|---|---|---|
| **Investigate** | Establish what is known, what conflicts, and what evidence answers a question. | Frame the question, reconcile sources, resolve evidence gaps, produce a grounded answer or investigation record |
| **Decide** | Resolve an open decision through challenge, evidence, and explicit trade-offs. | General and technical interviews, documented decisions, external questionnaires, decision rationale |
| **Plan** | Turn a destination into resolved decisions, specifications, and executable slices. | Multi-session decision maps, spec synthesis, ticket dependencies, transitions between uncertainty and execution readiness |
| **Design** | Develop and realize a product design, preserving its approved direction. | Direction interviews, rough experiments, wireframes, fidelity prototypes, motion, cinematic production, design commitments |
| **Implement** | Deliver a scoped change with the tracking and evidence the work needs. | Execution ownership, recovery, dependency frontier, implementation evidence, review and acceptance state |
| **Diagnose** | Establish the cause of a failure and prove the recovery. | Incident scope, reproduction, competing explanations, causal evidence, repair handoff and recovery checks |
| **Review** | Assess a change or interface and adjudicate findings against evidence. | Technical verdicts, static findings, motion and interface critique, fidelity comparison, distinct review axes |
| **Verify** | Check specified behavior and produce an inspectable evidence report. | Check selection, execution, expected/observed results, coverage, report data and rendering |
| **Describe** | Document how an existing product behaves and how that account was verified. | Outside-in behavior documentation, states, interrupts, evidence, unknowns, defect triage |
| **Communicate** | Explain, write, summarize, or hand off information for its intended audience. | Human-facing writing, concise explanation, critical briefings, readback, recap, durable handoff |
| **Learn** | Build understanding through visual explanation, practice, and retained learning. | One-session explanation and multi-session learning, lessons, exercises, learning records |
| **Coordinate** | Organize independent work and integrate its results into one coherent outcome. | Work decomposition, ownership, context briefs, clean-room assessment, result integration and recovery |
| **Configure** | Shape an agent working environment and verify that its capabilities fit the work. | Role and capability design, configuration intent, compatibility assessment, setup verification and handoff |

This restores a broad happy-path proposal. It is not a mandatory thirteen-stage pipeline. A user may enter any workflow directly, ask for several outcomes together, or invoke an independent capability. Broad coverage comes from conditional methods, not a long checklist imposed on every request.

## What each workflow contains

### Investigate

Add an AFK-owned investigation method: define the question and evidence standard, inventory relevant sources, distinguish disagreements from missing information, investigate the material gaps, and report the answer with its limits. Use independent Research for source gathering; Domain Modeling for terminology; Source Driven Development for version-sensitive technical claims; Truss or Doubt Driven Development when consequential uncertainty warrants their respective lenses.

The output is a resolved question or a precise account of what remains unknown. Investigation may support any other workflow without forcing a separate task or report. It does not silently become an interview, an incident response, or implementation. This is new workflow functionality around current capabilities, not a claim that the catalog already has a manual investigation source to absorb.

### Decide

Compose `grill-me`, `grill-with-docs`, `afk-code-grill`, and `to-questionnaire`. Preserve the differences between ordinary challenge, domain/ADR recording, technical trade-offs, and questions for someone who holds missing knowledge. Use independent Grilling, Domain Modeling, Codebase Design, and Truss at the corresponding boundaries.

AFK owns how evidence changes the decision, the accepted trade-off, rejected alternatives that matter, and the condition that would reopen it. Questionnaire mode collects the recipient and information gap; it does not repeat a full subject interview or send the document without authorization. Visual decisions are owned by Design, whose method can be used within an ongoing decision engagement without duplicating its source.

### Plan

Compose `wayfinder`, `afk-to-spec`, and `afk-to-tickets`. Preserve Wayfinder's actual decision graph, frontier, named decisions, and continuity; preserve spec synthesis and executable ticket contracts. These are conditional methods inside one planning workflow, not three mandatory stages.

AFK owns promotion from a coherent decision to a multi-session graph, convergence from the graph into a spec, and conversion from settled behavior into executable slices. Decision tickets and implementation tickets remain distinct. Settled intent can go straight to synthesis. A request to plan remains planning unless execution is also authorized.

Use Investigate or Decide for a specific open question, Design for a visual decision, and independent Prototype when an experiment supplies evidence. Preserve existing tracker adapters and source ownership. Do not duplicate decisions in both the map and tickets or create a second planning record merely because packaging changed.

### Design

Compose `afk-design-grill`, `afk-animated-driven-frontend`, `html-wireframe`, `html-prototype`, `apple-design`, and `animate-text`. This restores both ordinary product design and ambitious cinematic work. Carry useful scripts, effect specifications, assets, and mode references as needed, with source provenance; do not reduce those packages to summarized prose.

Design owns the brief, fixed application shell, variable surface, approved reference, must-preserve details, motion intent, and what each artifact can establish. It selects and executes a fitting method, then carries its decisions into realization or handoff. Its functionality includes visible alternatives, recorded visual commitments, bounded interactive artifacts, and cinematic production continuity.

Use **full independent Impeccable** for its relevant shape, craft, implementation, iteration, audit, polish, and other supported modes. Use independent **Prototype** for question-first rough or real-app experiments, **Design Artifact** for HTML craft, and **Animate** for bounded animation construction. AFK supplies the task, fidelity contract, and relevant rulings; it does not load all three whole systems indiscriminately.

Proposed rulings:

- Rough experiments answer structural or behavioral questions; they do not approve visual fidelity. File format and production framework do not decide the route.
- Wireframes compare structure. Fidelity prototypes establish the selected surface or bounded flow at the required states and viewports.
- The selected visual reference governs subsequent realization. An inherited preference for roughness cannot erase that commitment.
- Surface motion direction precedes component construction when direction is unresolved. A named component animation does not require a whole-surface redesign.
- Apple-derived interaction guidance informs gestures and continuity; it does not impose Apple's visual identity on every project. Animate Text's portable contracts do not authorize copying showcase chrome or demo copy.
- ADF's co-direction, binder, and creative gates belong to cinematic mode. Its Workprint exception remains explicit. Ordinary Design work does not inherit those waits.

Impeccable remains directly usable in full. Design provides AFK's engagement and cross-method continuity around it. Where a maintained dependency's instructions genuinely conflict with the selected contract, use a tested supported mode, narrow adapter, or separately traceable compatibility patch. Do not pretend a caller sentence reliably cancels every instruction inside an unchanged dependency.

If Prototype becomes manual, its material can join Design's experiment method structurally. That would centralize its upkeep without changing this user-facing capability or inventing another Mock entry. No invocation setting is changed by this proposal.

### Implement

Evolve `afk-implement` into this workflow, retaining its source identity where useful. Preserve its durable implementation record, interruption recovery, tracking ownership, acceptance contract, and exact review basis. Add clear integration with the revised Plan, Design, Review, Verify, and Coordinate contracts rather than creating a second tracking system.

Use independent TDD, Codebase Design, Source Driven Development, Code Simplification, Code Review, and relevant frontend capabilities conditionally. Keep tracked mode's intentional gates intact. Proposed direct mode supports a bounded implementation without durable tracking; it is an explicit adaptation, not an unnoticed weakening of the existing tracked workflow. Ordinary implementation outside the manual workflow remains available.

Design governs an approved visual commitment; Implement owns engineering completion and the execution record when it is the active delivery owner. A cinematic production retains its creative gates. Passing tests does not constitute creative approval, and a design selection does not establish implementation correctness.

### Diagnose

Add a manual AFK investigation-to-recovery workflow around independent `diagnosing-bugs`. It owns incident context, impact and scope, evidence that distinguishes causes, the boundary between diagnosis and authorized repair, and a reproducible recovery check.

Use Research or Source Driven Development where external behavior matters, Truss for consequential repair choices, and Verify for a requested reusable evidence report. A diagnosis-only request ends with evidence and a repair proposal; an authorized fix continues through repair and relevant checks. Independent Diagnosing Bugs remains the direct route for a focused debugging request. The umbrella's added value is coherent incident evidence and recovery, not relabeling that skill or requiring incident paperwork for every exception.

### Review

Compose `afk-code-review-verdicts`, `afk-static-review`, and `review-animations`, with selected PE interface, hostile-state, and fidelity material. Use independent AFK Code Review for Standards and Spec; use Impeccable's relevant review capabilities and Truss where appropriate.

Own the scope, evidence collection, per-finding adjudication, and distinction between technical correctness, fulfillment of intent, interface craft, and fidelity. Preserve the verdicts method's complete original review output and distinguish finding verification from discovering additional issues. A motion finding requested during Design uses this shared review method rather than a second diverging copy.

Review-only work does not silently change product code. An authorized fix request may continue into implementation. Scratch harnesses must have an appropriate permitted surface; adapting PE requires resolving its conflicting source instructions, not carrying both forward.

### Verify

Adapt PE Verify into a manual workflow with named checks, source revision and target, expected/observed results, execution evidence, explicit skipped/not-run states, and reusable report data/rendering. Integrate existing checks and browser capabilities instead of forcing one capture stack or viewport.

Verification supplies evidence to Implement, Diagnose, Describe, and Review. None must run the full reporting workflow when ordinary checks already meet the request. Schema validity is not execution evidence; source inspection is not a browser run. Existing reports are reused when their revision, target, and coverage remain applicable.

### Describe

Adapt PE Product Description into a manual workflow for existing product or feature behavior. Preserve outside-in flows, states, interrupts, terminology, source references, uncertainty, verification status, and suspected-defect triage. Support the repository's documentation location and bounded features.

Use independent Research and Domain Modeling plus Communicate's human-writing method, and Verify when observation is required. Keep intended behavior from Plan separate from observed or source-inferred behavior. Remove document-length targets and compulsory separate-repository scaffolding through recorded adaptations.

### Communicate

Compose `writing-for-humans`, `bro`, `facts`, `readback`, `recap`, and `handoff`. This deliberately reopens the earlier preference to keep human writing separate, following the request to reconsider all manual operations. Independent Writing for Agents remains available for agent-facing documents; it can be used behaviorally when that is the requested audience.

The package owns audience, purpose, precision, and the appropriate output form. Its methods preserve distinct behavior: simplify the last explanation; brief material implications; confirm the user's request; recap briefly; write an audience-appropriate document; transfer resumable context. Readback's confirmation is local to readback. Recap creates no obligatory file. Handoff points to existing artifacts instead of copying them.

AFK explicitly selects the audience before choosing the writing method; it does not concatenate the human and agent writing instructions. A user asking for a handoff should not get a polished article. Long-form writing and tiny conversational utilities load different references.

### Learn

Compose `teach` and `show-me`. Own the difference between a focused visual explanation and a stateful learning engagement, then add a coherent progression from explanation to practice and retained learning when requested. Preserve Teach's learning mission, lessons, resources, retrieval practice, and records without making them mandatory for “show me how this works.”

Use independent Research for source grounding and Design Artifact for useful HTML teaching material. A brief explanation remains brief. Communicate may use Learn's visual-explanation method when a diagram is the requested form, without copying its implementation or launching a curriculum.

### Coordinate

Compose `clean-room` with an AFK-authored coordination method. Use independent Architect before authorized spawning. Own bounded work assignments, context isolation, responsibility boundaries, result integration, and what to preserve across interruptions. Clean-room remains a specific neutral assessment with no inherited conversation and an unchanged returned verdict, not a default step for all delegated work.

Implement or Plan can use this method without making the user invoke Coordinate separately. They must still reach Architect at the actual spawning boundary. A reference to Architect in a source manifest cannot guarantee this. Direct Architect invocation remains available; Coordinate's added responsibility is the lifecycle and integration of a broader work arrangement.

Tool-specific advisor and cross-runtime packages stay independent. Choosing one as the execution tool does not make it an incorporated method or give it a parent umbrella. Preserve user and host authorization boundaries; organizing work alone does not authorize creating new user-owned tasks.

### Configure

Add an AFK-owned method for shaping a useful agent environment: establish roles and capabilities from the intended work, author the required behavioral definitions, identify compatible configuration surfaces, apply authorized setup, and verify effective behavior/state. Use independent Writing for Agents for authored instructions, Architect's expertise when role boundaries matter, and Wizard only for steps a human actually must perform.

AFK CLI, Profile Use, Create Agent, shadcn, Plannotator Guide, and Orchestrator remain independent tool packages. Configure does not absorb their docs or become their catalog “home.” It can use an explicitly relevant independent tool to carry out a chosen setup operation, just as Implement may use a compiler. Direct tool-specific requests still use the tool skill directly. Configure's authored value is work-to-environment design and verification, not another menu over AFK CLI commands.

## Conflict rulings are an authored part of the product

Use a maintained ruling reference for each relevant domain, with a small shared index. Put the runtime decision near its method and keep source history and maintenance details out of the hot path. A giant global conflicts document loaded for every invocation would recreate prompt debt.

Each ruling records the overlapping methods or contradictory guidance, the conditions selecting a method, the priority for those conditions, the preserved invariant, the source revisions involved, and what would reopen the decision. The maintained record and runtime instruction must agree. One ruling can govern multiple workflow callers; they must not grow independent contradictory copies.

Initial cross-workflow rulings proposed for this revision:

| Overlap | AFK ruling |
|---|---|
| Investigate / Decide / Plan | Establish evidence; resolve a choice; organize a destination. A task may cross these outcomes without repeating its intake. |
| Plan map / execution tracking | Decision tickets resolve uncertainty; implementation tickets deliver settled work. Convergence is explicit; planning does not implicitly authorize delivery. |
| Design / Impeccable | Design owns the selected AFK engagement and cross-artifact commitments. Impeccable performs its supported specialist work intact. Direct Impeccable use remains available. |
| Rough prototype / wireframe / fidelity prototype | Select by the uncertainty and review job. Preserve real-app context when material. No artifact approves more than it demonstrates. |
| Design / Implement | The approved design contract persists. Engineering delivery and creative acceptance are distinct; one active record owns each decision. |
| Review / Verify | Review judges; Verify establishes scoped evidence. Reuse applicable evidence, but do not turn a passing check into proof of all review axes. |
| Describe / Plan | Describe records actual or source-inferred behavior with evidence labels. Plan records intended behavior. Neither silently overwrites the other. |
| Communicate / Learn | A message, briefing, or handoff serves communication; an explanation with practice/progression serves learning. A visual explanation need not start a course. |
| Human / agent writing | Select by actual reader and use. Separate reference loading; mixed deliverables may use different methods for separate artifacts. |
| Coordinate / Architect | Coordinate owns the broader work arrangement; Architect governs actual authorized delegation. Every spawning path preserves that dependency. |
| Configure / tool skills | Configure owns environment intent and validation. Tool packages remain independent authorities for their interfaces, with direct invocation available. |

Known conflicts must be decided during authoring. A genuinely new conflict may require judgment or user input, but the workflow should surface the unresolved case and feed a maintenance ruling rather than pretending existing policy covers it. No catalog ruling overrides the user's instructions or the host's instruction hierarchy.

## Packaging, provenance, and migration

Keep the current canonical system while building an unpublished experimental tree. Port relevant current fixes deliberately so the replacement does not drift. Proposed layout for each workflow: a short root, selected methods, relevant policy references, necessary scripts/assets, and a source manifest. Final directory names and publication exclusions remain implementation decisions.

Record upstream repository and path, immutable commit, source checksum, carried-content checksum, classification (verbatim, patched, derived, or AFK-authored), pristine source plus patch or derivation record, and license/notice information. Track each source in multi-source methods. Maintain dependency compatibility information separately for independent capabilities. Existing catalog `composes` supports dependency selection; it does not establish source lineage or prove runtime invocation.

A later watcher can compare pinned inputs and create deduplicated reviewable issues or proposed updates. It must show which methods and rulings are affected. Humans validate adoption; accepted content and provenance change together. Hashes establish byte integrity, not semantic correctness. Build these records from the first incorporated source even if watching starts manually.

Ship a user-runnable migration tool with the eventual switch. It must identify AFK-managed installations, show mappings, preserve local modifications and recoverability, update relevant callers/profiles/rules, and be safe to rerun. Compatibility aliases target exact old operations, not ambiguous bare workflows. Never delete unrelated same-named skills or overwrite user-owned catalog choices. Tool packages and automatic entries are not retirement targets simply because they predate AFK Next.

The inventory currently proposes incorporating 26 manual entries into eight workflows, retaining six independent manual tool packages plus Compass, retaining nineteen automatic entries, and adding five workflows (Investigate, Diagnose, Configure, Verify, Describe). That is **39 logical catalog entries: thirteen manual workflows, seven independent manual entries, and nineteen automatic entries**. Retiring Compass would reduce this illustrative count to 38; no retirement is decided yet. The count is illustrative, not a design target, default-install count, or token-saving claim. IDs may be retained when an existing workflow evolves; aliases and profile installations affect actual discovery.

Profile-only packages and uncataloged authored skills are outside the 52-entry inventory, not deletion candidates. In particular, reconcile HTML profile packages and the uncataloged `afk-structured-debugging` before any old-tree cleanup. If Prototype's default is deliberately changed and its source incorporated, update this mapping and its callers, including Plan's inherited Wayfinder path, as an explicit migration decision.

## Prompt design and evaluation

The supplied Astra article supports a small root with conditional references; it does not require a small ambition or a package with no substantive methods. Descriptions identify the user's outcome. Detailed operation selection, artifact contracts, source adaptations, and relevant rulings live behind that entry. Do not expand a description into an inventory of all source skill names.

Keep instructions that preserve actual behavior: ADF's creative contract, clean-room isolation, review axes, evidence distinctions, and source fidelity. Remove redundant intake, arbitrary volume targets, repeated permission loops, and procedure that only compensates for older model behavior when evidence supports that adaptation. Manual invocation is not a reason to ignore instruction cost.

Validate both structural and behavioral composition before migration:

- Account for every old operation with an observable output/behavior case and, where retained, a direct-invocation case.
- Exercise the ambiguous pairs in the ruling table and confirm the selected method, loaded sources, dependency invocation, and result.
- Test Design with full Impeccable, rough versus fidelity prototypes, component versus cinematic motion, and an approved source carried into implementation.
- Test Plan from both open decision graphs and already settled specs; distinguish decision tickets from implementation slices.
- Test delegation entered through Plan or Implement as well as Coordinate; observe Architect use before spawning and clean-room context isolation.
- Test human versus agent writing, recap versus handoff, one visual explanation versus an ongoing learning engagement.
- Check aliases, missing dependencies, user invocation overrides, profile installation, source hashes, patch replay, and update impact reporting.
- Compare outcomes, unnecessary questions, references loaded, time, and measured token costs against current direct skills plus Compass. Test negative cases such as a typo that needs no elaborate workflow.

Do not test authored wording, headings, or example order. Deterministic checks cover schemas, paths, discovery, installation, provenance, and runtime behavior. Human evaluation judges artifact quality and decision fidelity. File validation of this proposal is not evidence that the future workflows work.

## Recommendation and next refinement

I prefer the manual-workflow strategy **in this broader form**: substantive AFK-owned operations and rulings, independent automatic expertise, and independently addressable tool packages. The structural boundary keeps automatic discovery available while still allowing AFK to own an entire engagement. That is closer to the useful PE inspiration than round two's mostly conservative regrouping.

The first refinement should examine the contents and handoffs of these workflows, not begin by excluding working skills. Design, Plan, and Implement show the strongest current foundation. Investigate, Diagnose, Coordinate, and Configure need authored methods that deliver the responsibilities described here; their presence is a positive proposal, not evidence those methods already exist. We can later merge, split, or retain direct entry points where experience suggests it, without treating thirteen as a quota.
